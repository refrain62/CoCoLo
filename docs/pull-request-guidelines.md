# Pull Request運用ルール

この文書は、CoCoLoのPull Request（PR）本文とレビュー運用の正本です。PR本文はGitHub上で表示される説明であり、コミットメッセージやレビューコメントの代替ではありません。

## 1. 適用範囲

- `develop`向けの機能・修正・文書PRに適用します。
- `main`向けのリリースPRは、リリース固有の確認事項を追加しても、共通7区画を維持します。
- 既存PRを更新する場合も、同じ形式へ移行します。
- 1つのPRには1つの目的だけを含め、別目的の変更は別PRへ分けます。

## 2. 本文の固定フォーマット

PR作成時は`.github/pull_request_template.md`を使用し、次の見出しをこの順序で1回ずつ置きます。

1. `## 概要`
2. `## 変更内容`
3. `## 影響範囲`
4. `## 検証`
5. `## レビュー観点`
6. `## 関連`
7. `## 残課題`

各区画は空にせず、該当なしの場合は`なし`と記載します。見出し名の変更、順序変更、同じ見出しの重複、区画外の`##`見出しは認めません。補助見出しが必要な場合だけ`###`以下を使用します。

本文の機械的な崩れを防ぐため、次も必須とします。

- 改行はLFに統一し、CRや文字列化された改行表記を含めない。
- 行末に空白やタブを置かない。
- 箇条書きは1項目1行を基本とし、項目の途中で手動改行しない。
- 検証コマンドと結果を同じ項目に記載する。
- token、パスワード、個人情報、productionの識別子やログ断片を本文に貼らない。
- 表を使う場合も、セル内へ長い改行を詰め込まず、必要なら箇条書きへ分ける。

## 3. 各区画の記載基準

### 概要

変更の目的、背景、利用者または運用上の効果を1〜3段落で記載します。実装手段の羅列から始めず、何を解決するPRかを先に書きます。

### 変更内容

コード、テスト、migration、Workflow、文書などの変更を責務単位で記載します。対象ファイルの全列挙ではなく、レビューで確認すべき契約・状態遷移・境界を優先します。

### 影響範囲

UI、API、DB、外部サービス、デプロイ、後方互換性、個人情報、テナント境界への影響を記載します。影響がない場合は、たとえば`実装コードと公開APIへの影響はなし（docs-only）`のように明記します。

### 検証

実行したコマンドと結果を記載します。最低限、変更に応じて次を確認します。

- `pnpm test`
- `pnpm build`
- 必要な場合の`pnpm typecheck`、`pnpm lint`、統合テスト、E2E、migration・RLS検査
- `git diff --check`

未実行の項目は隠さず、未実行の理由、代替確認、実行予定を記載します。

### レビュー観点

テナント越境、認可、個人情報、入力検証、状態遷移、競合・冪等性、テスト不足、仕様不整合を変更範囲に応じて確認します。該当しない観点も`該当なし（理由）`と記載します。

### 関連

機能仕様ID、Issue、依存PR、設計文書、レビュー記録をリンクまたは番号で記載します。関連がない場合は`なし`と記載します。

### 残課題

今回のPRで扱わない課題、後続PR、外部設定待ちを記載します。なければ`なし`と記載します。残課題を本文に書いた場合は、追跡先のIssueまたは台帳IDを付けます。

## 4. CIとレビューの仕組み

- ローカルでは`pnpm verify:pr-description`を実行して本文形式を確認します。
- PR品質Workflowでも同じ検査を実行します。
- 信頼境界ゲートは、base側の検証器でGitHub APIから取得したPR本文を再検査します。PRブランチ側で検証器を変更しても、この検査を回避できません。
- 検査に失敗したPRは、本文を修正してから再検証します。フォーマット不備をレビューコメントだけで例外扱いにしません。

検査器は内容の正しさやレビュー承認を判定しません。機能仕様、認可、テナント境界、個人情報、状態遷移、テスト結果の妥当性は、レビュアーが本文と差分を照合して判断します。

## 5. 既存PRの見直し手順

既存PRは次の順で確認します。

1. PRの状態、base、head SHA、差分の目的を記録する。
2. 本文を共通7区画へ移行し、内容を削除せず、改行と見出しを正規化する。
3. 検証結果、レビュー観点、残課題を差分とCIの実態に照合する。
4. `main`向け、古いbase、重複、クローズ済み、マージ済みの状態を変更せず記録する。
5. 変更後の本文を再取得し、`pnpm verify:pr-description`相当の検査を全件実行する。

マージ済み・クローズ済みPRも履歴として本文を整えますが、base、state、merge結果、レビュー履歴は書き換えません。内容の再現性を優先し、推測で検証結果やレビュー判定を補いません。
