# データベース分離仕様・移行計画

## 1. 目的と前提

現在の CoCoLo は、Supabase が提供する PostgreSQL をアプリケーションデータベースとして利用しています。将来、データベースを Supabase の管理範囲から分離し、別のマネージド PostgreSQL または自社運用 PostgreSQL へ移行できるように、ここで不変にする契約、移行手順、復旧方法を定めます。

この文書は「今すぐ移行するための作業指示」ではなく、移行時に設計判断がぶれないための仕様です。現行の外部サービス境界と日常運用は [外部サービス運用仕様](external-services-operations.md) を正本とします。

### 1.1 現在と将来の構成

```text
現在
利用者 ──> Web ──> API ──> Supabase Auth（認証）
                         └─> Supabase PostgreSQL（アプリDB、RLS、migration）
                         └─> Cloudflare R2（Phase 4で導入予定）

将来の分離後
利用者 ──> Web ──> API ──> Supabase Auth（認証を継続する場合）
                         └─> 分離先 PostgreSQL（アプリDB、RLS、migration）
                         └─> Cloudflare R2（オブジェクト保存を継続する場合）
```

分離後も、認証基盤とアプリケーションデータベースは別の責務です。Supabase Auth のユーザー情報を分離先 DB にコピーして認証情報を二重管理すること、ブラウザから分離先 DB に接続することは、この仕様の対象外かつ禁止事項です。

### 1.2 分離の非目的

- この文書だけで分離先のベンダー、リージョン、契約プランを決定しない。
- Supabase Auth の移行やログイン方式の変更を、DB分離に便乗して行わない。
- Cloudflare R2 の導入・移行を、DB分離と同じ変更として扱わない。
- Prisma のモデル名や API 契約を、分離先に合わせて変更しない。
- 本番の分離を、バックアップ復元と照合を省略したまま実施しない。

## 2. 分離時に守る不変契約

### 2.1 アプリケーション境界

アプリケーションコードから DB への入口は `packages/db` に限定します。API、ドメイン、Web が分離先のドライバー、管理者接続、SQL 方言を直接参照してはいけません。

分離先を変更しても、次の境界は維持します。

- `apps/web` は API と公開契約だけを利用し、DB URL、Prisma Client、Service Role Key を持たない。
- `apps/api` は認証済みのユーザー、テナント、RLS コンテキストを解決してから `packages/db` を呼び出す。
- `packages/domain` は DB 接続、環境変数、Hono、React、Prisma Client に依存しない。
- `packages/contracts` は DB の内部モデルをそのまま HTTP に公開しない。
- DB 固有の接続プール、migration、バックアップ復元処理はアプリケーションの公開 API に漏らさない。

### 2.2 認証ユーザー識別子

`tenant_memberships.user_id`、`guardian_members.user_id`、`audit_logs.actor_user_id` などの `user_id` は、Supabase Auth が発行する外部ユーザー識別子を文字列として保持します。Auth の内部テーブルへの外部キーや、Supabase の `auth` スキーマへの SQL 参照は作成しません。

この制約により、DB分離時はユーザー識別子を値として移行でき、認証プロバイダーの交換や Auth の別プロジェクト化でアプリ DB の外部キーを作り直さずに済みます。移行前後で識別子が変わる場合は、対応表を作成してからアプリ DB を移行し、対応表を監査証跡として保存します。

### 2.3 テナント分離とトランザクション

テナントをまたぐデータ参照を防ぐため、次の順序を分離後も保証します。

1. API が JWT からユーザーを検証する。
2. API がユーザーの所属テナントと権限を解決する。
3. DB トランザクション開始後、対象テナントをトランザクションローカルなコンテキストへ設定する。
4. RLS とアプリケーション側の認可を二重に適用する。
5. トランザクション終了時にコンテキストが残らないことを保証する。

接続プールを利用するため、セッション全体にテナントを設定してはいけません。`set_config(..., true)` 相当のトランザクションローカル設定を使い、ロールバック・例外・接続再利用時にも前テナントの値が残らないことをテストします。

### 2.4 migration とリリース

スキーマの正本は `packages/db/prisma/schema.prisma` と `packages/db/prisma/migrations` です。分離先の管理画面で手作業の DDL を実行して正本との差分を作ってはいけません。

- migration はリリース成果物に含め、コミット SHA と SQL のチェックサムを記録する。
- `DIRECT_URL` は migration 実行用、`DATABASE_URL` はアプリ実行用に分ける。
- アプリ実行ロールには DDL 権限を付与しない。
- migration の適用結果と失敗時の状態を CI/CD の証跡に残す。
- 破壊的変更は expand/contract で段階化し、旧アプリと新アプリが同じ期間に動いても成立する状態を先に作る。

## 3. 分離先 DB の最低要件

分離先の選定では、価格や管理画面の使いやすさだけでなく、次の要件を満たすことを確認します。未確認の項目は「対応済み」と記録せず、導入判定を保留します。

### 3.1 PostgreSQL 互換性

- 現行で検証している PostgreSQL 17 と互換性がある。
- UUID、JSON/JSONB、列挙型、複合ユニーク制約、外部キー、`ON DELETE RESTRICT` を利用できる。
- RLS、ポリシー、トランザクションローカルな設定、トランザクション、advisory lock を利用できる。
- アプリ側で生成する UUIDv7 の値を受け入れ、DBベンダー固有の UUID 生成関数には依存しない。
- Prisma が生成する SQL と `packages/db/prisma/migrations` の SQL を、staging 相当のデータ量で検証できる。

### 3.2 セキュリティとネットワーク

- API と migration 実行元を TLS で接続できる。
- 本番 DB は公開インターネットへ無制限に公開せず、private network、固定 egress、または厳格な IP allowlist を利用する。
- DB の管理者資格情報、アプリ資格情報、バックアップ暗号鍵を別々に管理・ローテーションできる。
- `cocolo_app` が RLS を迂回できないことを、ロール属性と実クエリの両方で確認できる。
- 監査ログ、接続ログ、管理操作ログを取得し、保持期間と参照権限を定められる。

### 3.3 可用性、バックアップ、運用

- 自動バックアップと point-in-time recovery（PITR）の有無、保持期間、復元先を確認できる。
- 本番と同じスキーマを別環境へ復元し、定期的にリストア検証できる。
- 接続数、プール、タイムアウト、TLS証明書期限、CPU、メモリ、ストレージ、replication lag を監視できる。
- 障害時に、DB停止・読み取り専用化・接続先切り替えの権限と手順が明確である。
- RPO（許容データ損失）と RTO（復旧目標時間）を業務責任者が承認できる。

## 4. 移行対象と対象外

### 4.1 移行対象

| 区分 | 対象 | 移行時の扱い |
| --- | --- | --- |
| アプリデータ | `public.tenants`、`tenant_memberships`、`members`、`guardian_members`、`audit_logs`、`promotion_runs` | 制約・インデックス・RLS・コメントを含めて移行 |
| migration 管理 | `_prisma_migrations` | 適用済み履歴と checksum を照合し、分離先の正本にする |
| 外部識別子 | `user_id`、`actor_user_id` | 値を保持。変更が必要な場合は対応表と監査証跡を先に作成 |
| 添付ファイル参照 | 将来の R2 object key、content type、サイズ、checksum、状態 | DBの参照メタデータを移行。オブジェクト本体は別の移行手順で照合 |
| 将来のアプリテーブル | 機能仕様に追加された `tenant_id` 付きテーブル | 機能の移行仕様で対象・順序・互換性を追加記録 |

実際の移行時は、移行対象テーブルを `schema.prisma` と本番の `information_schema` から棚卸しし、この表との差分を承認記録に残します。

### 4.2 移行対象外

- Supabase `auth.*` スキーマ、Auth のパスワードハッシュ、Auth のセッション、Auth の設定。
- Supabase の管理用スキーマ、ダッシュボード内部テーブル、サービス固有の拡張設定。
- `DATABASE_URL`、`DIRECT_URL`、Service Role Key、バックアップ鍵などの秘密情報。
- Cloudflare R2 のオブジェクト本体。R2を移行する場合は、キー一覧、checksum、サイズ、content type、公開可否を照合する別計画を作る。

対象外データを `pg_dump` で誤って取得・復元しないよう、dump のスキーマ・テーブル allowlist と除外条件をコマンドレビューで確認します。

## 5. 分離先のロールと権限

分離後も、少なくとも次のロールを分けます。実際のロール名を変える場合も、責務と禁止権限は維持します。

| ロール | 用途 | 付与する権限 | 禁止事項 |
| --- | --- | --- | --- |
| `cocolo_app` | API の通常処理 | 対象スキーマの必要な `SELECT/INSERT/UPDATE/DELETE`、RLS適用下の実行 | DDL、ロール管理、RLS迂回、バックアップ管理 |
| migration owner | CI/CD の migration | スキーマ変更、migration履歴更新 | アプリ実行、秘密情報のログ出力 |
| security owner | RLS・ポリシー・監査設定 | RLS、ポリシー、権限、監査設定の管理 | 日常のアプリデータ更新 |
| backup/recovery operator | バックアップ・復元 | バックアップ、PITR、復元、復元後の照合 | アプリ用接続文字列の共有 |

`cocolo_app` の `rolbypassrls` は `false` とします。移行直後に `current_user`、`current_database()`、`rolbypassrls`、許可された schema/table の権限を実クエリで記録します。

## 6. 推奨する移行方式

初回の分離は、書き込み停止を伴う「バックアップまたは論理 dump の取得、分離先への復元、照合、接続先切り替え」を基本方式とします。現状の監査ログ、年度繰り上げの冪等性、RLSコンテキストを考慮すると、準備なしの dual-write は採用しません。

dual-write や CDC が必要になるのは、停止時間が業務要件を満たさない場合だけです。その場合は、次を含む別の設計・敵対的レビューを完了してから採用します。

- 二重書き込みの片側だけ成功したときの再実行と補正。
- 監査ログが二重記録・欠落しないためのイベント ID と順序。
- RLSコンテキストを両接続へ同じ条件で渡す方法。
- 外部キー、ユニーク制約、idempotency key の競合解決。
- 新旧DBの差分を検知し、切り戻し後もデータを失わない手順。

## 7. 移行ランブック

本番作業は、作業責任者、アプリ担当、DB担当、セキュリティ確認者の承認を揃えて実施します。コマンドは作業記録へ保存し、秘密情報、接続文字列、JWT、個人情報をログへ出力しません。

### 7.1 事前準備

1. 分離先要件、リージョン、RPO/RTO、バックアップ保持期間、停止時間、費用、担当者を承認する。
2. 対象コミット、migration checksum、Prisma schema、Node.js 24、pnpm のバージョンを固定する。
3. 本番の DB、Auth、R2（導入済みの場合）の依存関係と、直近バックアップの復元可能性を確認する。
4. テナント数、各テーブルの件数、最大レコード、添付メタデータ件数を記録する。
5. 分離先へ接続する秘密情報を GitHub Environment または承認済みの秘密情報管理基盤へ登録する。チャット、リポジトリ、ビルドログへ値を記録しない。
6. staging で本番相当の dump/restore、RLS、冪等性、監査ログ、API smoke、E2E を実行し、証跡を保存する。
7. 作業中止条件、連絡先、切り戻し判定時刻、変更凍結期間を決める。

### 7.2 分離先の構築

1. TLS、ネットワーク制限、バックアップ、PITR、監視、アラートを設定する。
2. DB、schema、拡張機能、タイムゾーン、照合順序、接続数、statement timeout を確認する。
3. migration owner、security owner、`cocolo_app` を作成し、最小権限を付与する。
4. release artifact に含まれる migration を migration owner で適用する。
5. RLS、policy、index、constraint、table/column comment を、migration後の実体と正本で照合する。

### 7.3 データ移行と照合

1. 移行元の対象 schema/table allowlist を確定する。Supabase `auth.*` と管理用 schema を含めない。
2. 整合性のあるバックアップまたは論理 dump を取得し、取得時刻、対象、checksum、保管場所を記録する。
3. 分離先へ復元し、migration履歴、制約、インデックス、RLS、権限を再確認する。
4. テーブルごとの件数、主キーの最小・最大、`created_at`/`updated_at` の範囲、テナント別件数を比較する。
5. 外部ユーザー識別子、年度繰り上げの `idempotency_key`、監査ログの時系列、添付メタデータの object key/checksum を比較する。
6. 任意の2テナント以上で読み取りを行い、テナントAの認証済みリクエストからテナントBの行が見えないことを確認する。
7. 差分がある場合は原因を分類し、移行元を正とするのか補正するのかを承認してから次へ進む。差分を無視して切り替えない。

### 7.4 接続先切り替え

1. 書き込みを停止し、ジョブ、管理画面、バッチ、外部 webhook の再試行が書き込みを再開しない状態にする。
2. 移行元の最終 backup/差分 dump を取得し、最後の照合を行う。
3. API の `DATABASE_URL` を分離先へ変更し、`DIRECT_URL` を migration owner 用の接続先へ変更する。Auth用の URL と鍵は変更しない。
4. 秘密情報の反映後、同じ release artifact を再デプロイし、起動時の接続先と migration 状態を安全な識別子だけで確認する。
5. ヘルスチェック、ログイン、テナント一覧、作成・更新、権限拒否、監査ログ、冪等性、ファイル参照の smoke を実行する。
6. staging と production の配置記録、migration checksum、照合結果、作業者、時刻を一つの作業記録にまとめる。
7. エラー率、DB接続数、レイテンシ、ロック待ち、監査ログ出力を監視し、承認された時間だけ段階的に書き込みを再開する。

## 8. 切り戻しと復旧

### 8.1 書き込み再開前

新DBにアプリケーションの書き込みがないことを確認できる場合は、書き込み停止を維持したまま `DATABASE_URL` を移行元へ戻し、同じ成果物で再デプロイします。ヘルスチェックと照合を再実行してから書き込みを再開します。

### 8.2 書き込み再開後

新DBへ書き込みが発生した後は、接続先だけを戻す「盲目的な切り戻し」を禁止します。新DBの書き込みを止め、移行元との差分を抽出し、次のいずれかを承認して実施します。

- 新DBの変更を移行元へ補正反映してから移行元へ戻す。
- 新DBを正として障害を解消し、分離先で継続する。
- 承認済みの時点へ復元し、復元時点以降の利用者操作を再処理する。

監査ログ、年度繰り上げ、外部ファイル参照は特に差分を失いやすいため、上書きではなく event/idempotency key と作業記録を使って再処理します。復旧できない差分を削除して見かけ上合わせることはしません。

### 8.3 復旧後の確認

- API が分離先の `cocolo_app` で動作し、migration owner の資格情報を使っていない。
- `rolbypassrls=false` と、テナントA/Bの越境不可を実クエリで確認できる。
- 監査ログが欠落・重複していない。復旧操作自体も監査記録に残る。
- Auth のユーザー識別子と DB の外部キー相当値が一致している。
- 添付メタデータと R2 オブジェクトの存在、サイズ、checksum、非公開設定が一致している。
- バックアップから別環境へ復元できることを確認する。

## 9. 分離後の日常運用

### 9.1 変更管理

- schema変更は `packages/db/prisma/migrations` へ日本語の設計意図を残し、CIで checksum と適用順を検証する。
- production へは staging で検証した同一 release artifact を昇格する。
- 管理者による直接 DDL・直接データ修正は緊急時だけに限定し、承認、SQL、対象、結果、復旧方法を記録する。
- 破壊的な変更は expand/contract で実施し、旧版の稼働期間と contract 実施条件を文書化する。

### 9.2 バックアップと復元訓練

- バックアップの成功ではなく、定期的な復元テストの成功を復旧可能性の判定とする。
- 復元テストは、本番秘密情報をテスト環境へそのまま配置せず、資格情報を分離して行う。
- RPO/RTO、復元時刻、データ差分、RLS、権限、アプリ smoke の結果を記録する。
- 保持期限、削除期限、個人情報の扱いは、法務・運用方針と合わせて決定する。

### 9.3 接続と監視

- API はアプリ用ロールと接続プールを使い、migration用の直接接続を通常処理で使わない。
- 接続数、プール待ち、タイムアウト、トランザクション時間、ロック待ち、deadlock、ストレージを監視する。
- DB障害時に API が無限再試行して負荷を増やさないよう、接続タイムアウトと再試行上限を設定する。
- DB URL や SQL の bind 値などの秘密・個人情報をログへ出力しない。

## 10. 未決定事項と導入判定

本番分離の開始前に、次の項目を責任者が決定し、日付・承認者・根拠をこの文書または作業記録へ追記します。

| 項目 | 未決定の理由 | 決定時に残す内容 |
| --- | --- | --- |
| 分離先サービスと PostgreSQL 版 | 可用性・費用・運用体制の比較が必要 | ベンダー、版、契約、制約、検証結果 |
| リージョンとネットワーク | 個人情報、遅延、障害範囲に影響 | リージョン、経路、allowlist、TLS方式 |
| RPO/RTO | 業務責任者の合意が必要 | 目標、測定方法、未達時の判断 |
| 移行停止時間 | 利用者影響と整合性のトレードオフ | 開始・終了条件、告知、担当者 |
| バックアップ保持 | コストと復旧・削除要件に影響 | 世代、保持期間、暗号化、復元訓練周期 |
| dump/restore または移行ツール | データ量・停止時間で選択が変わる | ツール版、allowlist、checksum、ログ保管 |
| 障害時の責任分界 | 外部サービスとアプリの切り分けに必要 | 一次対応、エスカレーション、SLA |

次の条件を満たさない限り、本番切り替えを実施してはいけません。

- staging で全手順を再現し、Critical / High の指摘がゼロである。
- 対象・対象外の差分、件数・checksum・RLS・権限の照合記録が承認済みである。
- 切り戻しまたは forward recovery の判定条件と担当者が決まっている。
- バックアップからの復元とアプリ smoke が成功している。
- RPO/RTO、停止時間、秘密情報の保管場所、監視・アラートが承認済みである。
