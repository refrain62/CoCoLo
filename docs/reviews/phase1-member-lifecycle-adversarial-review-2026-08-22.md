# Phase 1部員ライフサイクルの敵対的レビュー

## 対象

対象コミットは、部員編集と退部の入力契約、API、RLS付きrepository、Web操作画面、単体テスト、統合テストです。

仕様上の対象は `FS-MEM-003` です。

## 確認項目

| 観点 | 確認結果 |
| --- | --- |
| テナント越境 | `tenantId`を入力から受け取らず、認証Contextと複合キーで対象を限定する。別テナントのIDは`null`結果から404になる。 |
| 認可 | 編集と退部を`owner`または`admin`に限定し、`staff`の拒否をAPIテストで確認する。 |
| 個人情報 | 公開DTOと監査metadataから`tenantId`、`note`、氏名、ふりがなを除外する。 |
| 入力検証 | UUID、未知キー、区分と学年または年代の不整合、状態値をAPI契約で拒否する。 |
| 状態遷移 | 通常編集は`active`または`suspended`だけを受け付け、`retired`への遷移を専用操作へ分離する。退部済みの通常編集は409にする。 |
| 競合 | 対象行を`FOR UPDATE`でロックしてから更新し、編集と退部を同一部員単位で直列化する。 |
| 監査 | 状態変更と監査INSERTを同一transactionで実行し、退部の再送も前後状態を監査する。 |

## 指摘と判定

### Critical

指摘なし。

### High

指摘なし。

### Medium

1. Web画面は所属roleを一覧APIから受け取らないため、権限のない利用者にも編集と退部ボタンが表示される。
APIが403で拒否するため認可 bypass にはならないが、誤操作を減らす表示制御は後続の所属情報表示と合わせて改善する。

2. 専用E2Eはテスト用部員IDとaccess tokenを設定したときだけ実行する。
通常のローカルE2Eでは実サービスの状態変更を避けるため、ライフサイクル操作自体は自動実行されない。

## 結論

CriticalとHighの指摘はなく、Phase 1の機能ブランチを次の統合工程へ進められる。

Mediumの2件は認可を弱めず、テスト用fixtureと所属情報APIを整備する後続課題として残す。
