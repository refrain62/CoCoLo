# コード説明・設計意図コメント監査

監査日: 2026-08-22

## 判定

`/docs` 配下の現行仕様を起点に、`origin/develop` に存在する API、認証、DB/RLS、共有契約、Web 画面、運用スクリプト、CI 検証コードを確認しました。

公開 API または責務が複雑な処理には、処理が何を保証するかを短く説明する日本語コメントを追加しました。また、テナント境界、認可、個人情報、入力検証、状態遷移、監査、デプロイ証跡など、コードだけでは前提を読み取りにくい箇所には設計意図を近接コメントとして記録しました。

本監査の範囲では、コメント不足に起因する Critical / High の指摘はありません。今回の変更は説明と設計意図の記録のみで、実行時の挙動は変更していません。

## 確認範囲

| 領域 | 記録した主な保証・設計意図 |
| --- | --- |
| API・認証・環境設定 | 認証済みコンテキストからのテナント決定、失敗時の情報隠蔽、必須設定の fail-closed、JWT の検証条件 |
| DB・RLS・監査 | トランザクション単位の RLS コンテキスト、同一トランザクションでの所属再確認、個人情報を検索語として保存しない境界、監査記録と更新の原子性 |
| 共有契約・ドメイン | 入力正規化、上限、相互排他条件、OpenAPI の生成元、学年・年齢表現の一元化 |
| Web | アクセストークンの扱い、ローカルプロキシの範囲、認証状態と画面状態の境界、API 成功後だけ一覧状態を更新する方針 |
| 運用・CI | 検証済み成果物の SHA 固定、環境・移行 SQL・依存関係・Workflow の検証を省略しない理由 |
| マイグレーション | 既存の日本語 `COMMENT ON`、JWT subject と所属の関係、guardian 関係の RLS 条件を確認 |

## 今後の適用ルール

- 自明な getter、単純なマッピング、設定値の列挙には過剰なコメントを追加しない。
- 公開 API や責務が複雑なメソッドには、利用者が確認すべき保証を日本語で短く記録する。
- 前提、制約、競合対策、テナント境界、認可、個人情報の扱い、状態遷移、トレードオフがコードから明らかでない場合は、近接コメントまたは `/docs` に理由を残す。
- コメントは実装の説明ではなく、コードだけでは失われやすい契約・設計判断を補足する。

## 検証

変更後に Node.js 24 を使用して `pnpm test`、`pnpm test:unit`、`pnpm typecheck`、`pnpm build` を実行し、結果を PR に記録します。
