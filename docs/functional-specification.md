## 1. この文書の役割

この文書は、CoCoLo が利用者に提供する機能、業務ルール、権限、状態遷移、受け入れ条件を定義する「何を作るか」の正本です。

* `docs/functional-specification.md`: 機能・業務仕様の正本。改修指示は機能仕様 ID を指定します。
* `docs/implementation-plan.md`: 技術方式、実装フェーズ、テスト、環境、CI の計画。
* `docs/resume-task-list.md`: 現行 `develop` の未完了タスクと停止条件。

仕様にない挙動を実装者の判断だけで追加せず、先にこの文書を更新します。仕様変更時は版、変更理由、影響する機能仕様 ID、データ移行の要否を記録します。

## 2. 用語と利用者

| 用語 | 定義 |
| --- | --- |
| チーム | CoCoLo を利用する部活・クラブチーム。データ分離の単位。 |
| 部員 | チームに所属する選手または一般参加者。 |
| 保護者 | 部員に紐づき、対象部員の情報確認や出欠回答を行う利用者。 |
| 役員 | 会長、会計、配車担当など、年度単位でチーム運営を担当する利用者。 |
| 管理者 | チーム設定、所属、部員、購買、個人情報を管理する権限を持つ利用者。 |
| スタッフ | 指導者・運営担当。予定や出欠の運用を行うが、個人情報と設定を管理しない。 |
| 当番 | 鍵開け、見守り、グラウンド準備など、予定ごとに割り当てる運営上の担当。 |
| 業務データの正本 | 予定、回答、割当、既読、注文、集金状態について、最新状態を確定する保存先。 |
| システム利用者 | OAuthで認証され、チームへの所属と操作権限を持つアカウント。 |
| 対象メンバー | 出欠、注文、送迎希望などの業務操作を帰属させる部員レコード。操作者と別に管理する。 |
| 機能契約 | チームのプランと個別設定から算出する、機能を利用できる状態。 |

### 2.1 表記ルール

* 本文でチームを利用する人は「利用者」と表記し、権限値としての `owner`、`admin`、`staff`、`guardian` はコード表記のまま記載します。
* API の項目名、状態値、環境名、コマンド名はバッククォートで囲み、画面や運用者に説明するときは日本語の意味を添えます。
* `local` は開発環境、`staging` は検証環境、`production` は本番環境を表します。環境名を省略する場合も、どの環境を指すか分かる表現にします。
* 「成果物」は配布・配置するリリースファイル、「配置アダプター」は環境固有のサービスへ成果物を配置する処理を指します。
* `E2E` はブラウザを通したエンドツーエンドテスト、`RLS` は行レベルセキュリティを指します。略語を初めて使う箇所では、必要に応じて日本語の意味を補います。

## 3. 共通業務ルール

### FS-COM-001 チーム分離

すべての情報はチーム単位で管理し、利用者は有効な所属を持つチームだけを操作できます。画面からチーム ID を書き換えても、別チームの情報を閲覧・変更できません。

### FS-COM-002 日時・年度

保存・判定の基準時刻は UTC、画面表示は `Asia/Tokyo` とします。年度は日本の年度（4月1日〜翌年3月31日）として扱います。締切判定はクライアント時刻ではなくサーバー時刻で行います。

### FS-COM-003 個人情報

氏名、ふりがな、電話番号、保護者との関係、特記事項は必要な権限へ最小限だけ表示します。閲覧、CSV出力、変更、退部処理は監査履歴へ記録します。Phase 1 の通常部員登録では特記事項を入力できません。

### FS-COM-004 状態と削除

利用中データは原則として物理削除せず、退部・停止・無効化などの状態で管理します。物理削除や匿名化が必要な場合は、保持期間と責任者の承認を確認してから実行します。

### FS-COM-005 資源IDとURL

API と画面 URL の資源 ID は連番ではなく UUIDv7 とします。UUID の値を知っていることだけでは認可にならず、すべての要求でログイン状態、所属チーム、役割、担当範囲を検証します。一覧や履歴の表示順は `createdAt` を正本とし、同じ時刻の並びを UUIDv7 で安定化します。UUIDv7 の生成時刻が推測できることを理由に、個人情報や別チームの存在を返してはいけません。

### FS-COM-006 WebとLINEの責務

予定、出欠、当番、配車、既読、注文、集金状態の正本は Web アプリとデータベースに置きます。

LINE は通知と対象画面への導線に使用し、LINE メッセージへの返信だけで業務状態を確定しません。

LINE 通知が失敗しても、Web で完了した業務更新を取り消しません。

通知本文には、電話番号、特記事項、未払い金額の詳細など、グループ参加者へ公開する必要がない個人情報を含めません。

### FS-COM-007 チーム単位の機能契約

機能の利用可否は、選択中のチーム、チームのプラン、個別のfeature flagからAPI側で算出します。

無償機能は初期値を持てますが、チーム単位でownerまたは許可された管理者が有効・無効を切り替えられます。

有償機能は有効なプランまたは承認済みの運用者による付与がある場合だけ利用できます。画面の表示制御だけで有償機能の利用可否を決めません。

feature flagのキー、プラン、変更者、変更理由、変更日時を監査し、未知のキーや判定不能な状態は無効として扱います。

機能が無効なチームのAPI、画面、通知、workerは業務データを処理せず、利用者には契約状態を確認できる安全なエラーを返します。

役員・連絡先は無料featureキー `board-contacts` で管理し、APIと管理メニューの両方を同じ契約状態に従わせます。

## 4. 認証・チーム利用

### FS-AUTH-001 ログイン

利用者は Supabase Auth でログインします。未ログイン状態では認証が必要な画面・操作を利用できません。期限切れ・署名不正・停止済み所属はログイン済みでも操作を拒否します。

### FS-AUTH-002 チーム選択

複数チームに所属する利用者は、操作対象チームを明示的に選択します。選択中のチーム名と役割を共通ヘッダーに表示します。

### FS-AUTH-003 所属状態

所属状態は `invited → active → suspended` と遷移します。`suspended` はログインできてもチームデータを操作できません。最後の owner を削除・降格できません。

### FS-AUTH-004 招待とOAuth連携

owner または admin は、対象メンバーに対する一回限りの招待を発行できます。

招待は対象チーム、対象メンバー、招待先の役割、発行者、有効期限、使用日時を持ち、別チームや別メンバーへ転用できません。

招待を受けた利用者は、招待URLを開いた後にSupabase AuthのLINEまたはGoogle OAuthで認証し、認証済みのprovider subjectを招待対象へ明示的に紐付けます。

メールアドレスだけを本人識別の根拠にせず、OAuth providerとsubjectの組を一意な外部識別子として扱います。

期限切れ、使用済み、取消済み、別チームの招待は受諾できず、招待tokenをログや画面へ表示しません。

### FS-AUTH-005 OAuthアカウントと所属の分離

一つのOAuthアカウントは複数チームへ所属できますが、操作対象チームを暗黙に選択しません。

OAuthアカウントの連携解除や停止は、業務データの削除とは別操作として監査します。

同じprovider subjectが既存の別メンバーや別チームへ紐付いている場合は、管理者の確認なしに付け替えません。

## 5. 部員管理（Phase 1 最小実用版）

### FS-MEM-001 部員一覧

owner、admin、staff は所属チームの部員を一覧できます。検索対象は氏名・ふりがな、絞り込みは category・status とします。guardian は紐づく部員だけを一覧できます。

一覧には氏名、ふりがな、区分、学年または年代、status を表示します。電話番号、保護者識別子、特記事項は staff と guardian に表示しません。

### FS-MEM-002 部員登録

owner または admin は氏名、ふりがな、区分、学年または年代、status を入力して部員を登録できます。チーム ID、部員 ID、作成日時、特記事項は利用者入力ではなくシステムが管理します。

必須条件:

* student は `gradeLevel` または仕様で定めた学年情報を持つ。
* adult は `ageGroup` を使用し、学年表示を要求しない。
* 名前は空文字・過剰な長さを拒否する。
* status の初期値は `active`。

### FS-MEM-003 部員編集・退部

owner または admin は部員の基本情報を編集できます。通常の編集で変更できる status は `active` と `suspended` です。退部は専用の退部操作で `retired` へ遷移し、既に retired の部員に同じ操作をしても結果は変わりません。

退部後の部員は通常一覧から非表示にできますが、管理者は履歴として検索できます。退部処理では変更前後の status、実行者、時刻を監査します。

### FS-MEM-004 学年表示

`formatGrade` の表示規則は次のとおりです。

| gradeLevel | 表示 |
| --- | --- |
| 1〜6 | 小1〜小6 |
| 7〜9 | 中1〜中3 |
| 10〜12 | 高1〜高3 |
| 13〜16 | 大1〜大4 |
| 17以上 | OB / 院生 |

category が adult の場合は gradeLevel ではなく ageGroup を表示します。

### FS-MEM-005 年度繰り上げ

owner または admin は年度末に、対象年度と実行内容を確認して繰り上げを実行できます。対象は `active` かつ `student` の部員だけで、gradeLevel を一度だけ +1 します。adult、retired、suspended は対象外です。

実行前の `preview` で対象件数を表示し、`execute` は `Idempotency-Key` を必須とします。同一チーム・同一年度の二重実行では保存済みの結果を返し、追加の変更は行いません。同じキーでリクエストハッシュが異なる再送は拒否します。`PromotionRun` は `preview → completed/failed`、失敗時の再試行は `failed → completed/failed` だけを許可します。17以上の表示、卒業・留年・退部の扱いは実行前の確認画面に表示します。

### FS-MEM-006 表示名と保護者連携

部員の `name` はチーム内の表示名であり、フルネームまたはチームが認めたハンドルネームを登録できます。

戸籍上の氏名であることを前提にせず、本人と保護者が認識できる名称を使用します。

owner と admin は、部員に紐づく保護者の表示名、関係、LINE 連携状態（未招待、招待中、連携済み、停止）を確認できます。

staff は運営に必要な範囲だけを確認し、guardian は自分の紐付けと担当部員だけを確認できます。

保護者と部員の紐付けは、owner または admin の招待か確認を経て確定します。

未認証の利用者や guardian に、担当外部員を紐付け候補として表示しません。

### FS-MEM-007 メンバー単位の利用者連携

一つの対象メンバーには、本人または確認済みの保護者など、複数の有効な利用者連携を登録できます。

本人利用者は自分に連携された対象メンバーだけを選択でき、guardianは確認済みの担当メンバーだけを選択できます。

出欠、注文、送迎希望などの保存データは、`actorUserId`（操作した利用者）と`subjectMemberId`（対象メンバー）を別々に記録します。

クライアントが任意の利用者IDや対象メンバーIDを送っても、APIは認証済み所属と有効な連携を再検証します。

## 6. 予定・出欠（Phase 2）

### FS-EVT-001 予定登録

owner、admin、staff は予定を登録・編集できます。予定はタイトル、種別（練習・試合・イベント）、開始・終了時刻、場所、持ち物、会費、案内画像、出欠締切を持ちます。試合では対戦相手、遠征では集合時刻と配車要否を追加できます。

### FS-EVT-002 予定表示

月間と週間の表示を切り替えられます。

月間表示は、日付、予定、時間と場所、当番、送迎、出欠と未回答を同じ日付行で確認できる表を基本とします。

練習は青、試合は赤、イベントと懇親会は紫で識別し、色だけに依存しない種別ラベルを併記します。

利用者自身の当番と送迎割当は、氏名または「自分」のラベルを付けて識別できるようにします。

スマートフォンでは主要情報を横スクロールなしで表示し、補足情報は同じ行の展開操作で確認できるリキッドレイアウトにします。

### FS-EVT-003 出欠回答

guardianまたは本人利用者は、有効なメンバー連携で選択した対象メンバーの出欠を、出欠締切前に `attending`、`absent`、`pending` のいずれかで登録・変更できます。締切後は本人利用者とguardianの変更を拒否し、owner、admin、staffは管理操作として修正できます。締切後の修正理由と実行者を監査します。

同一イベント・同一対象メンバーの回答は1件に統合し、最後の操作者と更新日時を記録します。管理者はチーム内の回答数と未回答者を確認できます。

### FS-EVT-004 出欠締切とリマインド

予定には出欠回答の締切を設定でき、締切日時と未回答状態を予定一覧と詳細に表示します。

owner、admin、staff は、対象予定、対象者、送信予定時刻、通知手段を確認してリマインドを登録できます。

同じ予定、対象者、通知種別、予定時刻の登録は一件に統合し、再操作や worker の再試行で重複通知しません。

LINE が未接続の場合も Web 上の未回答表示は利用でき、通知操作は「未接続」として扱います。

送信結果、失敗理由、再試行、取消は監査できる状態で記録します。

### FS-EVT-005 場所と地図

予定は場所名に加えて、住所または管理者が確認した地図 URL を登録できます。

利用者は予定詳細から地図を開けます。

地図連携が未設定または障害中の場合も、場所名と住所を確認できます。

利用者が入力した任意の URL を検証せずにリンクとして表示しません。

### FS-EVT-006 回答対象の選択

複数の対象メンバーへ連携された利用者は、回答前に対象メンバーを明示的に選択します。

対象メンバーの一覧には、利用者が閲覧を許可された表示名だけを示し、別チームや未確認の連携を候補に含めません。

対象メンバーを選択できない場合は回答を保存せず、既存の回答を別メンバーへ付け替えません。

## 6.1 当番管理（Phase 2）

### FS-DUT-001 当番枠と割当

owner、admin、staff は予定ごとに、鍵開け、見守り、グラウンド準備などの当番枠、必要人数、説明を登録できます。

当番枠には同一チームの有効な利用者だけを割り当てられます。

同じ利用者を同じ当番枠へ重複して割り当てず、予定または利用者の状態が変わった場合は確定前に再検証します。

割当の追加、変更、解除は、変更前後、実行者、時刻を監査します。

### FS-DUT-002 当番一覧と担当回数

利用者は月間予定で当番の役割と担当者を確認できます。

利用者自身の担当は、色だけに依存しない表示で強調します。

owner、admin、staff は対象期間内の利用者別担当回数を確認できます。

担当回数は調整材料であり、公平性の自動判定や自動確定の根拠にはしません。

## 7. 役員・連絡先（Phase 3）

### FS-BRD-001 年度役員

owner または admin は年度、役職名、担当者、役職種別を管理できます。新年度には前年度の役職枠だけを複製し、担当者・個人連絡先は自動コピーしません。

役員の割当とアプリの操作権限は別に管理し、役員へ割り当てたことだけを理由に `owner`、`admin`、`staff` を付与しません。

`board-contacts` が無効なチームでは、役員・連絡先のAPIと管理メニューを利用できません。

### FS-BRD-002 連絡先表示

電話番号の表示設定は `line`、`phone`、`both` から選択します。`line` は電話番号を表示せず、`phone` は電話番号を表示し、`both` は両方を表示します。owner と admin には設定に応じた連絡先を表示し、staff と guardian には役職名・役職種別だけを表示して連絡先値を表示しません。

## 8. 共同購買・集金（Phase 3）

### FS-ORD-001 商品・選択肢

owner または admin は募集案件、商品、価格、画像、任意の選択肢を登録できます。選択肢は商品ごとに定義し、キッズサイズ、大人サイズ、フリーサイズなどを混在させられます。注文時の選択値は登録済み選択肢に限ります。

キッズサイズ、大人サイズ、指定なしのプリセットは入力補助として提供できますが、保存する選択肢は管理者が確認した商品ごとの値を正本とします。

選択肢がない商品では、注文画面に選択を要求しません。

### FS-ORD-002 注文

本人利用者またはguardianは、有効なメンバー連携で選択した対象メンバー、自分の注文者情報、商品、選択肢、数量、背番号、背ネームを入力できます。数量は1以上、背番号・背ネームは商品の入力条件に従います。別チームの商品や別注文の商品明細は登録できません。

### FS-ORD-003 集金

オンライン決済は使用せず、現金手渡しまたは銀行振込の確認状態を管理します。owner または admin は未払いから支払い済みへ切り替え、確認日時と確認者を記録できます。支払い済みを未払いへ戻す場合も監査します。

### FS-ORD-004 集計・CSV

管理者はサイズ・選択肢別の数量、支払い状態、未払い者を確認できます。CSV は UTF-8 BOM 付きとし、セル先頭の `=`, `+`, `-`, `@` を式として実行されない形式に変換します。

CSV には、発注に必要な場合だけ対象部員、商品、選択肢、数量、背番号、背ネームを含めます。

電話番号、LINE 識別子、特記事項は既定の CSV に含めません。

### FS-ORD-005 未払い者への通知

owner または admin は、募集案件ごとの未払い者と通知対象を確認してからリマインドを登録できます。

通知登録は同じ募集案件、対象者、通知種別、予定時刻について一件に統合します。

LINE が未接続の場合は「未接続」、送信に失敗した場合は「送信失敗」と表示し、集金状態を変更しません。

グループ通知には個人名、個別注文、未払い金額を掲載せず、対象者だけが認証後に詳細を確認できるリンクを使用します。

### FS-ORD-006 注文対象と操作者

注文には対象メンバーと操作者を別々に保存します。

同じ募集案件、同じ対象メンバー、同じ冪等キーの再送は一件に統合し、別の対象メンバーへの注文へ変更しません。

guardianが複数の対象メンバーを管理する場合も、注文確認と集計は対象メンバー単位で分離します。

## 9. 添付・回覧・通知（Phase 4）

### FS-FIL-001 添付

添付ファイルはチーム専用の非公開ストレージに保存します。許可形式、マジックバイト、実体サイズを検証し、SVG は受け付けません。利用者へ公開 URL を保存・配布せず、権限確認後に短期 URL でダウンロードさせます。

### FS-FIL-002 添付アップロードの手順

利用者が添付を開始すると、API は所属・権限・許可 MIME・最大20 MiBを確認し、TTL（有効期間）900秒の一回限りのアップロードセッションと署名 URL を発行します。Web は署名 URL で非公開ストレージへ直接 PUT し、API の `complete` 操作を呼び出します。API はセッションの所有者、チーム、オブジェクトキー、期限、未使用、上書き不可、実体サイズ、マジックバイト、SHA-256 を再検証します。`complete` の再試行は同じセッションで3回までです。検証成功時だけ `uploaded → available` とし、期限切れ、再利用、別チーム、改ざん、形式不正は `rejected` として24時間以内に保存本体を削除します。

### FS-FIL-003 商品画像と予定画像

owner または admin は共同購買の商品に画像を添付でき、owner、admin、staff は予定とイベントに案内画像を添付できます。

画像は FS-FIL-001 と FS-FIL-002 の非公開添付として保存し、DB に公開 URL を保持しません。

権限を持つ利用者は商品カードと予定詳細で画像をプレビューし、拡大表示できます。

画像がない場合、読み込みに失敗した場合、利用権限がない場合を区別し、代替テキストを表示します。

### FS-ANN-001 回覧板

owner、admin、staff は連絡事項と PDF 等の資料を掲載できます。利用者は本文と添付を確認し、確認時刻を記録します。掲載者は未読者一覧を確認できます。

### FS-NOT-001 LINE通知

LINE連携は、CoCoLoのチームと、そのチームのBotが参加するLINEグループを紐付ける機能です。

通知機能は個人のLINEアカウントを配信先としてCoCoLoへ紐付ける機能ではなく、公式アカウントや個人LINEへの配信は現行仕様の対象外です。LINE OAuthによるシステムログインはFS-AUTH-004で別に扱います。

利用開始時は、運用者がLINE Messaging APIのchannel、Webhook、Botのグループ参加を設定し、ownerまたはadminがCoCoLoへLINEグループIDを登録します。

通知用LINEグループIDの自動検出、QRコードによるグループ接続、LINE OAuthによるグループ接続は現行実装にありません。

LINE連携が設定されたチームでは、予定の作成時に予定通知と出欠締切通知を登録し、予定の更新時には出欠締切通知を登録します。

予定の作成と更新はowner、admin、staffが実行できますが、通知登録は予定の保存と同じ業務transactionへ組み込みます。

現行のWeb画面と汎用通知APIによる手動通知登録および再送はownerとadminだけが実行できます。

owner、admin、staffが回覧を掲載すると、`line-notifications`が有効で接続済みグループがある場合に回覧通知を同じ業務transactionへ自動登録します。staffが汎用通知を手動登録する権限と、未払い通知のproducerは別タスクとして扱います。

通知登録前に対象チーム、通知先、対象資源、通知種別を確認し、同じ業務操作の再送を一件に統合します。

未設定はエラーではなく「未接続」と表示し、送信失敗は再送可能な状態で記録します。

Webhook は署名、重複、接続世代、対象チームを検証します。

Webhookは受信receiptの記録と重複排除を行う入口であり、LINEメッセージへの返信だけで予定、出欠、回覧、集金の状態を確定しません。

通知本文は概要と認証済み deep link を基本とし、グループへ不要な個人情報を掲載しません。

現行の中央producerは、通知先が現在接続中のグループであること、通知元資源が同じチームに属すること、公開アプリの許可originと固定パスからdeep linkを生成することをサーバー側で検証します。

workerも送信前に同じ通知元境界を再検証し、旧形式または不正なoutbox行は送信せず隔離します。

### FS-NOT-002 LINEからWebへの遷移

LINE 通知のリンクは、通知対象と同じチームの Web 画面へ遷移します。

未ログイン、セッション期限切れ、別チーム選択中の場合は、認証とチーム選択を完了してから対象画面へ戻します。

LIFF を利用できない端末または通常ブラウザでも、同じ認証と認可を経て対象画面を開けるようにします。

リンクに認可情報や長期 token を含めず、資源 ID を知っていることだけで閲覧を許可しません。

対象が削除済み、期限切れ、権限外の場合は、その理由に応じた復旧可能な画面を表示し、別チームの存在を推測させません。

## 10. 送迎（Phase 5）

### FS-RIDE-001 配車希望

利用者は車を出せるか、乗車可能人数、乗車希望を登録できます。

車を出せる場合の乗車可能人数は、運転者を除く実際の空席数として1人以上20人以下で登録します。

車を出せない場合と未回答の場合は、提供枠を登録しない状態と未回答状態で区別します。

管理者は希望人数と容量を確認し、手動または補助機能で割り当てます。

補助機能は割当案を作成するだけで、管理者が確認するまで確定または公開しません。

割当結果、未割当、変更履歴を、権限を持つ利用者へ表示します。

### FS-RIDE-002 配車表の確定と公開

配車表は `draft → open → closed → finalized` の順に遷移します。

`open` で提供枠と乗車希望を受け付け、`closed` で管理者が割当内容を確認し、`finalized` で利用者へ確定結果を公開します。

公開後の変更は、理由を記録して `finalized → closed → finalized` と再確認します。

確定時に、同じ部員の重複割当、車ごとの定員超過、無効な提供枠、別チームの利用者を拒否します。

割当確定と提供枠の変更が競合した場合は、古い内容で上書きせず再確認を求めます。

一般利用者へ表示する配車表には、運転者名、集合情報、担当部員など運用に必要な情報だけを含め、電話番号、自宅住所、車両番号を既定では表示しません。

## 11. 状態遷移

### FS-STATE-001 状態遷移の正本

| 対象 | 状態 | 遷移条件 |
| --- | --- | --- |
| 所属 | invited → active | 招待受諾・管理者承認 |
| 所属 | active → suspended | 管理者が停止 |
| 招待 | pending → accepted / expired / revoked | OAuth受諾、期限切れ、管理者取消 |
| メンバー連携 | invited → active → revoked | 招待受諾、連携解除・停止 |
| チーム機能 | disabled ↔ enabled | 有効な機能契約または許可された設定変更 |
| 部員 | active ↔ suspended | 管理者の状態変更 |
| 部員 | active / suspended → retired | 退部操作 |
| 出欠 | pending ↔ attending / absent | 締切前の回答 |
| 通知 | pending → sending → sent / failed / unknown | workerのclaim、provider応答、送達不明 |
| 注文 | open → closed → completed | 締切・発注完了 |
| 集金 | unpaid ↔ paid | 管理者の確認 |
| 年度繰り上げ | preview → completed / failed、failed → completed / failed | owner/adminのexecute、同一年度の再実行は保存済み結果 |
| 添付 | uploaded → available → deleted | 検証成功・認可・削除 |
| 添付 | uploaded → rejected | マジックバイト・サイズ・形式の検証失敗 |
| 配車表 | draft → open → closed → finalized | 受付開始・受付終了・管理者の確認と公開 |
| 配車表 | finalized → closed → finalized | 公開後変更の理由記録・再確認・再公開 |

状態遷移にない直接変更、利用者による状態の書き換え、締切後の本人変更は許可しません。`deletedAt` は `deleted` のときだけ設定し、`rejected` は配信・署名 URL 発行の対象にしません。

## 12. 画面共通仕様

### FS-UI-001 モバイル表示とアクセシビリティ

* 読み込み中、データなし、入力エラー、通信エラー、権限不足、保存成功を区別して表示します。
* 必須項目、エラー理由、フォーカス位置、キーボード操作を利用者が確認できます。
* 色だけで状態を伝えず、ラベルやアイコンを併用します。
* 個人情報を含む操作、退部、支払い状態変更には確認を求めます。
* local、staging、production の環境名を画面または管理情報で識別でき、staging のデータを本番と誤認させません。
* 月間予定、部員、役員、購買、集金、配車の主要操作は、スマートフォンの縦画面で横スクロールせず完了できます。
* デスクトップでは比較用の表を使用でき、モバイルでは列を消すだけでなく、同じ行の情報を優先順に再配置します。
* 氏名、当番、未回答、支払い状態をアイコンまたは色だけで表現しません。
* ダイアログ、選択欄、通知、画像拡大表示は、フォーカス移動、閉じる操作、代替テキストを提供します。

### FS-UI-002 管理画面のメニューと画面分離

管理画面は一枚の画面へ機能を詰め込まず、ダッシュボード、メンバー、予定・出欠、購買・集金、回覧・添付、LINE、チーム設定、機能契約を独立したルートと画面へ分けます。

メニューは利用者のroleとチームのfeature flagから生成し、利用できない機能を操作可能に見せません。

各画面は一覧、検索、詳細、作成・編集、保存結果、エラー、空状態を同じ情報設計で示し、対象メンバーの選択状態を画面遷移後も明示します。

管理操作は確認、実行中、成功、失敗、再試行の状態を持ち、二重送信を防ぎます。

### FS-UI-003 共通UIコンポーネントとデザイン

共有UIは`packages/ui`へ集約し、shadcn/uiの設計思想に沿った、アクセシブルで再利用可能なコンポーネントとして管理します。

ボタン、入力、select、dialog、table、カード、ナビゲーション、通知、状態表示、メンバー選択を共通コンポーネント化し、画面ごとの独自styleと色定義を増やしません。

デザイントークン、タイポグラフィ、余白、角丸、境界線、フォーカス、色の意味を一つのテーマで管理し、無料・有償機能や権限不足の状態も同じ視覚規則で表示します。

主要画面は390px、430px、768px、1280px以上で確認し、キーボード操作、visible focus、コントラスト、reduced-motion、44px以上を目安にした操作領域を受け入れ条件にします。

## 13. 受け入れ条件

### FS-ACCEPT-001 受け入れ条件の正本

* FS-COM-001〜006 のチーム分離、日時、個人情報、状態、資源 ID、Web と LINE の責務が守られる。
* FS-AUTH-001〜005 の認証、所属、停止状態、招待、LINE・Google OAuth、provider subjectの境界がすべて検証される。
* FS-COM-007 のチーム単位feature flag、プラン境界、無効時のAPI・画面・worker停止が検証される。
* FS-MEM-001〜007 の部員一覧、登録、編集、退部、学年表示、年度繰り上げ、表示名、保護者連携、メンバー単位の利用者連携が権限・状態遷移どおりに動作する。
* FS-EVT-001〜006 の予定、対象メンバー選択、締切前出欠、締切後拒否、集計が動作する。
* FS-EVT-004〜005 と FS-DUT-001〜002 のリマインド、場所、月間表、当番割当、担当回数が権限と重複防止どおりに動作する。
* FS-ORD-002、FS-ORD-005〜006、FS-FIL-003、FS-NOT-001〜002 の対象メンバー単位の注文、通知対象、非公開画像、deep link、未接続、送信失敗が仕様どおりに動作する。
* FS-RIDE-001〜002 の定員、重複、競合、確認、公開、再公開が動作し、配車表に不要な個人情報が表示されない。
* 個人情報の表示範囲、監査、添付の非公開配信、CSV の安全性が確認できる。
* FS-UI-001〜003 の主要操作をモバイルの縦画面、キーボード、色を識別しにくい条件で完了でき、管理画面のルート分離と共通UIの再利用を確認できる。
* `local` で TDD、`staging` で結合テスト・E2E テスト、本番で承認済み成果物の昇格が行える。
